## 从一段很小的代码出发

```c
int main() {
  return 2 + 3;
}
```

这段程序对人来说没有太多歧义。但机器并不直接理解 `return` 或 `2 + 3` 的源代码写法。编译器需要在保持程序语义的前提下，将它转化成目标机器能够执行的形式。

一条典型的理解路径是：源代码 → 词法与语法分析 → 抽象语法树 → 中间表示 → 目标代码。真实的编译器会根据语言和目标平台增加更多阶段，也不一定严格按这条线单向推进。

## 语法树保留了什么

源代码首先被分解成词法单元，随后根据语法规则组合成结构。抽象语法树保留的是程序的关键语义结构，而不是每一个分隔符的原始写法。

对于上面的例子，可以从树上看到一个函数、一条返回语句，以及一个以整数常量为操作数的加法表达式。

这样一来，处理程序就不再是处理一长串字符，而是访问有明确类型和关系的节点。

## 为什么需要中间表示

如果语法树已经描述了结构，为什么不直接生成机器指令？因为源语言的表达方式和目标机器的执行方式之间，通常还有很大的距离。

中间表示提供了一个较稳定的抽象层，让前端关注源语言语义，后端关注目标架构，也让分析与变换有一个更合适的工作对象。

例如，一个简化的中间表示可能先表达“将两个值相加，再返回结果”。如果编译器在某个阶段进行了常量折叠，也可能直接变成“返回整数 5”。

> 同一个语义，可以有不同的表示。边界越清楚，越容易判断变换有没有改变原来的意思。

## 正确性藏在边界上

一个很小的例子能跑通，不代表所有边界都正确。随着语言功能增加，编译器还需要处理作用域、类型、控制流、函数调用和存储布局等问题。

学习时，可以为每一层问三个问题：

1. **输入是什么？** 是字符、语法节点，还是已经定义好的中间表示？
2. **这一层承诺了什么？** 哪些语义已经确定，哪些决定留给下一层？
3. **如何观察结果？** 能否查看中间输出，并用一个最小程序定位问题？

当最终汇编出了错，沿着这些边界向前检查，通常比只盯着最后的输出更容易找到原因。

## 用最小程序建立理解

给程序一次只增加一个特性：先是常量返回，再是表达式，然后是局部变量、分支与循环。每增加一步，就观察抽象语法树、中间表示和目标代码发生了什么变化。

这样的实践能把“编译器有很多阶段”变成一组具体、可检查的对应关系。
